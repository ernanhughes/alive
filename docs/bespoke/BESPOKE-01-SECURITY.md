# Security and authority boundaries

Recommendation is not authorization. Selection is not execution. YAML is data. Browser
content cannot select its own capability set, install implementations, widen permissions,
change goals or mint owner grants. Unavailable dependencies remain unavailable regardless of score.

## Evidence

`tests/test_bespoke.py` exercises strict requests/YAML, exact source hashes, cross-instance and
cross-goal/inquiry/source substitution, source withdrawal, grant revocation, missing capability
and workflow states, permission and resource conflicts, future status, exact recipe pins,
historical replay, changed recipes/workflows/capabilities/policy, altered records, zero model
side effects and actual controlled handoff through WorkflowRunner.

Captured text containing system-message spoofing, fake GitHub identity, capability YAML,
network/plugin requests, goal/grant instructions and injected code comments remains source data.
The test's trusted fixture owner explicitly approves each modified content hash; selection still
preserves the explicit objective and abstains when browser procedures are unavailable. It neither stores the hostile prose
in the rationale nor dispatches a model. Unapproved substitution is tested separately and refused.

The dashboard uses React text rendering and the existing graph component. Unit tests cover
malicious names, empty context/catalogue, missing history, backend outage, credential changes,
and late responses. Real desktop/mobile browser tests assert historical graph inspection and
Observatory navigation issue no execution writes.

## Trusted host handoff

`trusted_handoff` is an in-process laboratory integration, not a production approval API. It
revalidates record integrity, exact live recipe and selection policy, source/goal/inquiry/principal,
the complete candidate including current binding and deployment policies, the separately supplied
grant's workflow/binding identity, and the recommendation's resource envelope. Only then does it
record an identity link and return the existing authorization ID. It still does not execute.

The host calls `WorkflowRunner.start` and `execute`; the runner independently performs its normal
grant/configuration/source/revocation/claim/admission checks and rechecks before stages. The new
handoff grants no capability. Its event link is not evidence of successful or authorized execution;
the real run and existing receipts remain authoritative. History only links runs matching the
instance, goal, inquiry, exact workflow, source and retained handoff identity.

## Residual risks and nonclaims

- Production source consent/owner authorization remains unavailable. Do not expose laboratory
  fixture grant creation as an HTTP endpoint or describe it as a qualified approval workflow.
- One bearer token authorizes the instance's owner view. This is not a multi-user ACL system.
- Trusted Python code, database administrators and the existing event writer remain trusted.
  ORM immutability and integrity hashes do not defend against an administrator rewriting all data.
- Existing capability fingerprint transitivity limitations from PI-03A remain unchanged.
- A controlled-source match or valid reference does not establish semantic truth. Workflow
  completion does not establish objective success or produce independent feedback.
- Model-assisted selection, document ingestion, source crawling, semantic validation, adaptive
  workflow composition and automatic learning are absent.
- The implementation-authored mutation receipts are not an independent adversarial review.
  The independent reviewer must supply additional mutations before approving this milestone.
