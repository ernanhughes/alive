## What was connected

Before ALIVE-09, feedback changed only exact goal/URL/excerpt recall. It did not update a persisted
policy that a later nonidentical decision could consult.

ALIVE-09 adds:

- `companion-feedback-usefulness-v1` in `alive/web_experience.py`;
- a persisted policy row of kind `policy` in the existing `WebExperience` table;
- context-level useful/not-useful counts keyed by `goal_id|url|language`;
- minimum support 3 and suppression at useful rate <= 0.20;
- policy version/hash and recommendation recorded on snapshots and notes;
- idempotent duplicate feedback and one-update revision semantics;
- explicit `owner_correction=true` analysis for lexical and feedback-policy no-action states;
- persisted correction rows;
- extension panel support for policy visibility and "Analyse anyway";
- policy-version before/after display after feedback.

Exact validated useful recall remains authoritative and takes precedence over adaptive suppression.

## Feedback contract

A feedback row hangs off a validated note, which hangs off the reviewed snapshot. The note already
records goal, URL, excerpt hash, grant, Governor reservation and model usage. The feedback row records:

- useful/not useful;
- goal/URL/language context string;
- revision status and previous rating;
- policy version/hash before and after;
- whether the source note came from an owner correction.

Semantics:

- same rating repeated: returns the existing feedback row with `idempotent=true`; no policy update;
- different rating: updates the latest feedback row, replaces its prior count in the same context,
  and increments the policy exactly once with `revision=true`;
- retraction is not a separate endpoint; a revised rating is the defined correction mechanism;
- factual truth is not inferred from usefulness. Exact quotation validation remains independent;
- no synthetic feedback is generated by the runtime.

The latest feedback row for a note is used so legacy duplicate rows do not hide a newer rating.

## Policy contract

- Policy ID: `companion-feedback-usefulness-v1`.
- Context: `goal_id|url|language`.
- Minimum independent support: 3 ratings.
- Suppression: support >= 3 and useful rate <= 0.20.
- Insufficient support: retain `analyse`.
- Above 0.20: retain `analyse`.
- Policy history: bounded to 50 updates.
- Policy state is a JSON row; no database migration.
- A suppression returns `no_action`, `no_action_source="feedback_policy"`, no note and no provider
  reservation.

The policy cannot grant permission, expand the allowlist, bypass the Governor, choose a model,
alter budgets or reuse an unvalidated note.

## Owner correction

`POST /api/v1/browser-experience/analyse` accepts `owner_correction` on `AnalyseRequest`.

The request still requires:

- the reviewed excerpt hash;
- an active, unexpired exact-page grant;
- the existing Governor call/token/cost checks;
- no other active cognitive worker.

The correction is recorded against the snapshot with prior action, relevance status, policy
version/hash and reason. It does not create permanent permission, does not bypass validation and
does not imply the resulting note was useful.

Controlled sequence, 5 synthetic provider calls across two contexts:

1. three related excerpts analysed, policy v0 -> v3;
2. three not-useful ratings, context 0 useful / 3 not useful;
3. fourth excerpt returns `no_action` with `feedback_policy`; zero calls;
4. direct analysis without correction returns HTTP 409; zero calls;
5. owner correction produces one bounded note;
6. useful feedback updates policy to v4, context 1 useful / 3 not useful (0.25);
7. fifth excerpt returns `analyse` again;
8. a separate context exercises duplicate and revised feedback;
9. restart preserves policy v6, rejects the pre-restart grant with 403, keeps note count 5 -> 5 and
   does not replay inference.

The baseline replay is decision-level only. It shows the trade-off: suppression saves a call when
history is right and can miss a useful analysis when it is wrong. It is not a powered outcome study.

## Limitations and review focus

- Controlled API/SQLite evidence with a synthetic provider; no native browser, no Meta inference.
- Minimum support 3 is conservative; one useful correction can end suppression.
- Policy context is exact goal/page/language, not semantic topic generalisation.
- Decision-level baselines do not establish better task outcomes.
- The companion still covers only two exact documentation pages.
- No browser-history ingestion or cross-device inference.
- ALIVE-08 remains negative on its primary comparison; its post-hoc always-retrieve `0.0747` is not
  a preregistered result and is not used as an ALIVE-09 advantage claim.

Review checklist:

1. Confirm feedback revisions cannot double-count.
2. Confirm owner correction cannot bypass grant expiry, revocation or Governor budgets.
3. Confirm exact useful recall still precedes adaptive suppression.
4. Confirm no provider call occurs on a suppressed decision.
5. Confirm archive manifest hashes and unchanged prior archives.
6. Confirm no merge or auto-merge is enabled.
